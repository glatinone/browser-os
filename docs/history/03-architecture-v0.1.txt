 # Browser-OS Architecture

 > **Status:** Architecture Specification\
>  **Version:** 0.1\
>  **Project:** Browser-OS\
>  **Primary goal:** Build a high-performance, local-first execution layer between AI agents and the modern web.

---

 # 1\. Executive Summary

 Browser-OS is an **AI-native browser execution runtime**.

 It is not:

 - a new browser engine
- a browser UI
- an LLM
- a browser automation clone
- a screenshot-based computer-use system

 Browser-OS sits between an AI agent and a real browser.

```
┌─────────────────────────────────────────────┐
│                  AI AGENT                   │
│                                             │
│ GPT / Gemini / Claude / Local Agent / etc.  │
└──────────────────────┬──────────────────────┘
                       │
                       │ Browser-OS API
                       ▼
┌─────────────────────────────────────────────┐
│                 BROWSER-OS                 │
│                                             │
│  Agent Runtime                              │
│  Action Router                              │
│  DOM Intelligence                           │
│  Memory / Cache                              │
│  Session Manager                             │
│  Security / Policy                           │
│  Observability                               │
└──────────────────────┬──────────────────────┘
                       │
                       │ CDP / Playwright
                       ▼
┌─────────────────────────────────────────────┐
│              REAL BROWSER                  │
│                                             │
│ Chrome / Chromium / Edge                    │
│                                             │
│ Persistent Profile                          │
│ Cookies                                     │
│ LocalStorage                                │
│ Extensions                                  │
│ Authentication                              │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
                    INTERNET
```

 The central architectural principle is:

 > **Use the cheapest and most deterministic mechanism capable of completing the action.**

 Execution priority:

```
Cache
  ↓
Deterministic DOM/CDP
  ↓
Semantic DOM reasoning
  ↓
Fast/small LLM
  ↓
Vision / Computer Use
  ↓
Human takeover
```

 # 2\. Core Design Principles

 ## 2.1 AI is not the default executor

 Do not invoke an LLM for an action that can be executed deterministically.

 Bad:

```
LLM
 ↓
click
 ↓
LLM
 ↓
type
 ↓
LLM
 ↓
scroll
```

 Preferred:

```
Task
 ↓
Router
 ↓
known workflow
 ↓
direct browser actions
```

---

 # 2.2 DOM before vision

 The system must prefer structured browser information over screenshots.

 Preferred:

```
DOM
 ↓
semantic extraction
 ↓
element resolution
```

 Only use vision when DOM-based methods fail or are insufficient.

---

 # 2.3 Real browser before alternative browser engines

 The default browser runtime is:

 - Chrome
- Chromium
- Edge

 The system must prioritize compatibility with real-world websites over synthetic browser benchmarks.

 This is especially important for:

 - Microsoft Entra
- Google SSO
- LinkedIn
- Instagram
- Salesforce
- Slack
- internal enterprise applications
- extensions
- WebAuthn/passkeys
- complex SPAs

 Alternative browser engines such as Lightpanda may be supported later as optional providers.

---

 # 2.4 Persistent sessions are first-class

 Browser-OS should treat browser sessions as persistent resources.

 Do not create a fresh browser for every task unless explicitly requested.

 Preferred:

```
Browser Manager
     │
     ├── Profile A
     ├── Profile B
     ├── Profile C
     └── Profile N
```

 Profiles may contain:

 - cookies
- localStorage
- sessionStorage
- extensions
- browser settings
- authentication state

---

 # 2.5 Learn successful workflows

 Every successful workflow should have the opportunity to become cheaper and faster.

 First run:

```
Task
 ↓
Explore
 ↓
Reason
 ↓
Execute
 ↓
Record
```

 Later run:

```
Task
 ↓
Cache
 ↓
Execute
```

 The system should progressively reduce:

 - LLM calls
- tokens
- screenshots
- DOM processing
- browser startup
- reasoning latency

---

 # 2.6 Everything should be replaceable

 Vendor-specific components must not leak into the core architecture.

 Use interfaces for:

```
BrowserProvider
ModelProvider
VisionProvider
ActionExecutor
MemoryProvider
CacheProvider
SessionProvider
```

 This allows the project to change:

 - browser
- model
- automation library
- storage
- AI provider

 without rewriting the entire system.

 # 6\. Agent Runtime

 The Agent Runtime receives high-level instructions.

 Example:

```
"Open LinkedIn and search for John Smith."
```

 It converts this into a task.

 The Agent Runtime should NOT directly manipulate Chrome.

 Instead:

```
Agent Runtime
      ↓
Task Router
      ↓
Action Planner
      ↓
Action Executor
```

 This separation is critical.

 # 11\. CDP Layer

 Location:

```
browser/cdp/
```

 CDP is the low-level browser control layer.

 Use CDP for:

 - Runtime
- DOM
- Page
- Input
- Network
- Target
- Storage
- Browser

 The CDP layer should remain thin.

 Do not build an entire browser automation framework on top of CDP unless there is a concrete reason.

---

 # 12\. Playwright Layer

 Location:

```
browser/playwright/
```

 Playwright provides high-level browser automation.

 Use it when:

 - selectors are reliable
- navigation is required
- frame handling is needed
- browser abstractions simplify implementation
- reliability is more important than micro-optimization

 CDP should be preferred when direct protocol access materially reduces overhead.

---

```

 Interface:

```
interface ActionExecutor {

    action: BrowserAction,

 # 14\. Action Representation

 Actions should be structured.

 Example:

```
{
  "type": "click",
  "target": {
    "elementId": "e_382"
  }
}
```

 Not:

```
"click somewhere around x=383 y=412"
```

 Coordinates should be a fallback.

 # 18\. DOM Compression

 Never send raw page HTML to an LLM.

 Pipeline:

```
HTML / DOM
    ↓
DOM parser
    ↓
interactive elements
    ↓
semantic normalization
    ↓
visibility filtering
    ↓
relevance filtering
    ↓
context compression
    ↓
LLM
```

 Example compressed context:

```
{
  "page": {
    "url": "https://example.com",
    "title": "Example"
  },
  "elements": [
    {
      "id": "e1",
      "role": "textbox",
      "name": "Search"
    },
    {
      "id": "e2",
      "role": "button",
      "name": "Submit"
    }
  ]
}
```

 # 19\. Action Router

 Location:

```
core/router/
```

 This is the central Browser-OS innovation.

 The router chooses the cheapest viable execution method.

```
                    ACTION
                       │
                       ▼
               ┌──────────────┐
               │ Cache lookup │
               └──────┬───────┘
                      │
                success?
                 /       \
               yes        no
                │          │
                ▼          ▼
             execute      DOM
                           │
                       success?
                        /     \
                      yes      no
                       │        │
                       ▼        ▼
                    execute   Fast LLM
                                 │
                              success?
                              /     \
                            yes      no
                             │        │
                             ▼        ▼
                          execute   Vision
                                      │
                                   success?
                                   /     \
                                 yes      no
                                  │        │
                                  ▼        ▼
                               execute   Human
```

---

 # 20\. Router Policy

 The router must optimize for:

 1. reliability
2. latency
3. cost

 Default ordering:

```
cached deterministic
>
direct DOM
>
Playwright/CDP
>
small model
>
vision
>
human
```

 The exact policy may evolve based on benchmarks.

---

 # 21\. Action Cache

 Location:

```
memory/
cache/
```

 The cache stores successful execution strategies.

 Example:

```
{
  "site": "linkedin.com",
  "intent": "open search",
  "strategy": {
    "method": "aria",
    "role": "textbox",
    "name": "Search"
  }
}
```

---

 # 22\. Trajectory Cache

 A trajectory represents a successful sequence.

 Example:

```
{
  "intent": "search LinkedIn",
  "steps": [
    {
      "action": "click",
      "target": "Search"
    },
    {
      "action": "fill",
      "target": "Search",
      "valueSource": "user"
    },
    {
      "action": "press",
      "key": "Enter"
    }
  ]
}
```

 Sensitive user data must NOT be persisted unless explicitly authorized.

---

 # 23\. Cache Validation

 Every cached action must be validated before execution.

 Validation:

```
element exists
element visible
element enabled
semantic identity matches
page context matches
```

 If validation fails:

```
cache miss
 ↓
DOM discovery
 ↓
AI fallback
 ↓
update cache
```

 Never blindly execute stale selectors.

---

 # 24\. AI Runtime

 Location:

```
ai/
```

 The AI layer must be provider-agnostic.

 Interfaces:

```
interface ModelProvider {
  complete(request: ModelRequest): Promise<ModelResponse>;
}

interface VisionProvider {
  analyze(request: VisionRequest): Promise<VisionResponse>;
}
```

---

 # 25\. Model Routing

 Models are divided by capability.

```
Planner
Fast Reasoner
Extractor
Vision
```

 Example:

```
models:
  planner: capable-model
  fast: low-latency-model
  extraction: small-model
  vision: vision-model
```

 No provider should be hardcoded into the core.

---

 # 26\. Fast Model

 The fast model is primarily used for:

 - element selection
- small decisions
- DOM interpretation
- recovery
- action validation

 It should receive minimal context.

---

 # 27\. Planner Model

 The planner handles:

 - complex tasks
- multi-step reasoning
- ambiguous instructions
- workflow decomposition

 The planner should not execute every individual click.

---

 # 28\. Vision Layer

 Location:

```
ai/vision/
```

 Vision is a fallback.

 Use it for:

 - canvas
- inaccessible controls
- visual-only interfaces
- difficult rendering
- DOM failure

 Vision should not become the default interaction mechanism.

---

 # 29\. Human-in-the-Loop

 Human takeover is a supported execution state.

```
AGENT
  ↓
security challenge
  ↓
PAUSED
  ↓
USER ACTION
  ↓
RESUME
```

 Typical cases:

 - MFA
- CAPTCHA
- passkey
- biometric confirmation
- security approval
- irreversible action confirmation

 Browser-OS must not attempt to bypass security mechanisms.

 # 31\. Extension Architecture

 # 35\. Security Architecture

 Sensitive information should remain outside model context wherever possible.

 Never expose unnecessarily:

 - cookies
- session tokens
- passwords
- API keys
- OAuth tokens
- browser profile secrets

 The browser should perform authenticated actions directly.

 The model should receive:

```
"Click the authenticated user's Settings button"
```

 not:

```
"Here is the user's session cookie..."
```

---

 # 36. Permission System

 Actions should have risk classifications.

```
LOW
MEDIUM
HIGH
```

 Examples:

 ### LOW

 - search
- navigate
- read
- extract

 ### MEDIUM

 - send message
- upload file
- modify record

 ### HIGH

 - delete
- financial transaction
- account permission changes
- irreversible operations

 Policies should allow:

```
permissions:
  low: auto
  medium: auto
  high: confirm
```

---

 # 37\. Observability

 Every operation should emit structured events.

 Example:

```
{
  "taskId": "task_123",
  "sessionId": "session_456",
  "action": "click",
  "method": "cache",
  "latencyMs": 8,
  "llmCalls": 0,
  "success": true
}
```

 Track:

 - action latency
- DOM extraction latency
- model latency
- token usage
- browser latency
- retries
- failures
- cache hit rate
- vision usage

---

 # 38\. Performance Architecture

 Performance optimization priorities:

```
1. avoid unnecessary work
2. avoid unnecessary model calls
3. avoid unnecessary DOM processing
4. avoid screenshots
5. reuse browser sessions
6. reuse learned trajectories
7. minimize IPC overhead
8. minimize serialization
9. use CDP for hot paths
10. parallelize independent operations
```

---

 # 39\. Performance Targets

 These are engineering targets, not guaranteed benchmark results.

 ### Cached action

 Target:

```
<20ms agent-side overhead
```

 ### Deterministic action

 Target:

```
<100ms agent-side overhead
```

 ### DOM reasoning

 Target:

```
<1 second
```

 ### Browser startup

 Prefer:

```
warm session
```

 over:

```
cold browser startup
```

 All targets must be measured with reproducible benchmarks.

---

 # 40\. Parallelism

 Independent browser operations may execute concurrently when safe.

 Example:

```
Tab A → extraction
Tab B → extraction
Tab C → extraction
```

 But actions affecting the same page must preserve ordering.

 The scheduler should distinguish:

```
read-only
```

 from:

```
mutating
```

 operations.

---

 # 41\. Failure Recovery

 Every action should have a recovery strategy.

 Example:

```
cached selector
       ↓
failed
       ↓
semantic DOM
       ↓
failed
       ↓
fast model
       ↓
failed
       ↓
vision
       ↓
failed
       ↓
human
```

 Retries must be bounded.

 Never endlessly repeat failed actions.

 # 52\. Browser-OS Kernel Concept

 The lowest-level Browser-OS runtime can be considered the "kernel":

```
Browser Kernel
├── Session Manager
├── CDP Manager
├── Page Manager
├── Action Executor
├── Permission Manager
└── Event Bus
```

 Above it:

```
AI Runtime
├── Router
├── Planner
├── Model Providers
├── Vision
└── Memory
```

 Above that:

```
Applications / Agents
├── Research Agent
├── CRM Agent
├── Social Agent
├── Coding Agent
└── Custom Agent
```

 This is the intended long-term architecture.

 # 63\. Definition of Architectural Success

 The architecture is successful if:

 1. A real Chrome/Edge session can be attached.
2. Existing authentication state remains usable.
3. Common browser actions work without AI.
4. DOM can be compressed into useful semantic context.
5. AI is only used when deterministic execution fails.
6. Successful workflows can be cached.
7. Repeated workflows become measurably faster.
8. Vision is optional rather than mandatory.
9. Security-sensitive actions can pause for human interaction.
10. Components can be replaced independently.
11. Performance can be measured at every layer.
12. The system can support both simple websites and complex enterprise applications.

 # 64\. Final Architecture Principle

 Browser-OS is fundamentally an **execution optimization system**.

 The objective is not:

```
"How can we make the LLM smarter?"
```

 The objective is:

```
"How can we make the LLM unnecessary for as much of the browser task as possible?"
```

 The ideal execution path is:

```
User intent
    ↓
Learned strategy
    ↓
Deterministic action
    ↓
Browser
```

 AI should appear only where uncertainty exists.

 The long-term goal is therefore:

```
FIRST RUN

AI-heavy
████████████████████

AFTER LEARNING

AI-light
████░░░░░░░░░░░░░░

MATURE WORKFLOW

Mostly deterministic
█░░░░░░░░░░░░░░░░░
```

 This is the core idea of Browser-OS:

 > **Maximum browser capability with minimum AI overhead.**
