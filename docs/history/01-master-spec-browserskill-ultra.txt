 # BrowserSkill Ultra

 ## 0\. Project Identity

 **Working name:** BrowserSkill Ultra\
 **Type:** Open-source, local-first, high-performance AI browser automation platform\
 **Primary goal:** Build a browser agent that combines the compatibility and authenticated-session capabilities of a real Chrome/Edge browser with an aggressively optimized AI/action layer.

 ### One-sentence definition

 > BrowserSkill Ultra is a local-first browser agent that controls real Chrome/Chromium/Edge sessions through CDP, uses deterministic automation whenever possible, invokes AI only when necessary, preserves real authenticated browser state, and dynamically escalates from cached actions → DOM → lightweight reasoning → vision/computer-use.

 ### Core philosophy

 **Do not use AI when code can do the job.\
 Do not use vision when DOM can do the job.\
 Do not use a large model when a small model can do the job.\
 Do not launch a new browser when an existing session can be reused.\
 Do not throw away knowledge that was already learned.**

 The system should become faster and cheaper as it learns repeated workflows.

---

 # 1\. Problem

 Current browser agents typically have one or more of these problems:

 1. They use an LLM for almost every browser action.
2. They repeatedly inspect screenshots.
3. They discard knowledge between runs.
4. They create new browser sessions unnecessarily.
5. They have difficulty preserving real-world authentication state.
6. They are expensive for long workflows.
7. They are slow on modern SPA applications.
8. They struggle with enterprise applications, SSO, MFA, extensions, complex DOMs, iframes, shadow DOM, and dynamic interfaces.
9. Browser automation tools are often optimized either for deterministic automation OR autonomous AI agents, rather than combining both.
10. Benchmark performance often focuses on browser startup/rendering rather than total agent latency.

 The project aims to solve this by separating:

 - browser execution
- action selection
- reasoning
- memory
- authentication/session management
- visual fallback

 # 5\. Architectural Principle

 ## 5.1 Execution hierarchy

 Every action should follow this priority:

```
1. Cached action
2. Deterministic Playwright/CDP
3. DOM semantic reasoning
4. Lightweight LLM
5. Vision/computer-use model
6. Human takeover
```

 The system must never jump directly to an expensive AI operation if a cheaper reliable method is available.

---

 # 6\. Browser Layer

 ## Primary browser

 Use real Chromium-based browsers:

 - Chrome
- Chromium
- Edge

 The browser must remain a first-class citizen.

 Do not make a lightweight browser engine the default for complex websites.

 Lightweight engines such as Lightpanda may become an optional optimization for compatible workloads, but they are NOT the primary browser for the MVP.

 ## Why

 Real browser compatibility matters more than synthetic browser benchmarks for:

 - enterprise SSO
- authentication
- extensions
- WebAuthn
- passkeys
- cookies
- browser policies
- complex JavaScript
- modern SPAs
- anti-bot mechanisms
- real user sessions

 # 7\. Browser Session Model

 The browser should support persistent sessions.

 Instead of:

```
launch browser
→ login
→ task
→ close
```

 the system should support:

```
Browser Manager
    ├── Profile A
    ├── Profile B
    ├── Profile C
    └── Profile N
```

 Each profile can contain:

 - cookies
- localStorage
- sessionStorage
- extensions
- browser settings
- authentication state

 The system must be able to reconnect to an existing browser session through CDP.

 - launch browser

 # 10\. CDP

 CDP is the low-level browser communication layer.

 Use CDP where direct browser protocol access provides lower overhead than higher-level abstractions.

 Possible operations:

 - DOM
- Runtime
- Input
- Page
- Network
- Browser
- Target
- Storage

 Playwright remains useful for high-level reliable browser automation.

 The system should not artificially choose between Playwright and CDP.

 Instead:

```
High-level stable operation
        ↓
Playwright

Low-level performance-critical operation
        ↓
CDP
```

---

 # 11\. DOM Observation Engine

 The agent should NOT send the entire DOM to the LLM.

 Instead:

```
Raw DOM
   ↓
Parser
   ↓
Interactive element extraction
   ↓
Semantic compression
   ↓
Relevant subset
   ↓
LLM
```

 Example:

```
{
  "buttons": [
    {
      "id": 12,
      "role": "button",
      "name": "Search"
    }
  ],
  "inputs": [
    {
      "id": 22,
      "placeholder": "Search"
    }
  ]
}
```

 The goal is to reduce:

 - tokens
- latency
- model cost
- hallucination
- context size

 # 12\. Semantic Element Model

 Every interactive element should receive a stable internal ID.

 Example:

```
{
  "element_id": "e_382",
  "tag": "button",
  "role": "button",
  "text": "Search",
  "aria_label": "Search",
  "visible": true,
  "enabled": true,
  "bbox": {
    "x": 120,
    "y": 80,
    "width": 90,
    "height": 32
  }
}
```

 The agent reasons over these IDs rather than raw coordinates whenever possible.

 # 13\. Action Cache

 This is one of the most important differentiators.

 If the system successfully performs:

```
LinkedIn
→ Search
→ enter query
→ click result
```

 store the successful trajectory.

 Example:

```
{
  "site": "linkedin.com",
  "workflow_hash": "...",
  "steps": [
    {
      "intent": "open search",
      "strategy": "aria",
      "selector": "..."
    }
  ]
}
```

 Next execution:

```
same intent
     ↓
trajectory cache
     ↓
execute
```

 No LLM required unless the cached strategy fails.

---

 # 14\. Cache Invalidation

 Never blindly trust cached selectors.

 Validate:

 - element exists
- element is visible
- element is enabled
- semantic attributes remain compatible

 If validation fails:

```
cache
 ↓
fail
 ↓
DOM discovery
 ↓
LLM
 ↓
new strategy
 ↓
update cache
```

 The system should learn from website changes.

---

 # 15\. AI Router

 The AI router determines how much intelligence is required.

 Example:

```
Can cached action execute?
    YES → execute

NO

Can DOM semantics resolve target?
    YES → execute

NO

Can small model resolve target?
    YES → execute

NO

Use vision/computer-use

NO

Human takeover
```

 This router is central to performance.

 Vision is explicitly a fallback mechanism.

 Use it when:

 - DOM is insufficient

 # 23\. Security Model

 Security is a first-class requirement.

- session tokens
- passwords

 # 26\. Performance Goals

 Performance is a first-class product feature.

 ## Target

 ### Deterministic action

 Target:

 **\<100 ms median action overhead**

 Ideal:

 **\<50 ms**

---

 ### Cached action

 Target:

 **\<20 ms agent-side overhead**

 excluding network/site latency.

---

 ### DOM reasoning

 Target:

 **\<1 second**

 for a simple element-resolution task.

---

 ### Vision fallback

 Target:

 **only when required**

 and measure separately.

---

 ### Browser startup

 Prefer:

```
warm browser
```

 over repeatedly launching Chromium.

---

 # 27\. Cost Goals

 The system should minimize model calls.

 Ideal task:

```
10 browser actions
0–1 LLM calls
```

 rather than:

```
10 browser actions
10+ LLM calls
```

 Long-term target:

 > Repeated workflows should approach deterministic automation cost.

 # 39\. Failure Recovery

 The agent should recover automatically.

 Example:

```
cached selector
     ↓
failed
     ↓
re-query DOM
     ↓
failed
     ↓
small model
     ↓
failed
     ↓
vision
     ↓
failed
     ↓
human
```

 Never blindly repeat the same failed action.

---

 # 40\. Learning Loop

 Successful recovery should update the system.

```
Task
 ↓
Action
 ↓
Success
 ↓

 ↓
Cache
 ↓
Next task
 ↓
Faster
```

 Failed strategies should also be recorded:

```

 ↓

 ↓
discover replacement
```

 # 41\. Long-Term Goal

 The long-term goal is not merely:

 > "another browser agent."

 The goal is:

 > **A browser execution runtime where AI reasoning is progressively removed from repeated work.**

 The first time:

```
AI-heavy
```

 After learning:

```
AI-light
```

 After repeated execution:

```
almost deterministic
```

 This creates a system that becomes:

 - faster
- cheaper
- more predictable
- more reliable

 over time.

 # 45\. MVP Acceptance Criteria

 The MVP is considered successful when:

 ### Browser

 - can attach to an existing Chrome/Chromium session
- can preserve authenticated profile
- can handle multiple tabs
- can recover from browser disconnect

 ### Automation

 - common DOM actions work reliably
- actions are executable without LLM

 ### AI

 - model can select elements from compressed DOM
- model is not called for deterministic actions
- vision is optional fallback

 ### Memory

 - successful workflows can be cached
- cached workflows execute without unnecessary LLM calls
- invalid cache entries can recover

 ### Performance

 - deterministic action overhead target \<100 ms
- cached action overhead target \<20 ms
- no unnecessary screenshot generation
- no unnecessary LLM calls

 ### Compatibility

 Demonstrate successful workflows on at least:

 - LinkedIn
- Microsoft Entra
- one complex SPA
- one SSO application
- one multi-tab workflow

 # 47\. AI Harness Instructions

 When an AI coding agent receives this document, it must:

 1. Read the entire specification.
2. Inspect the repository before modifying code.
3. Search for existing OSS implementations before reinventing components.
4. Prefer mature OSS libraries.
5. Verify licenses.
6. Implement interfaces before concrete integrations where practical.
7. Keep components replaceable.
8. Write tests for every major component.
9. Add benchmarks for performance-sensitive code.
10. Never optimize based solely on assumptions.
11. Measure before and after optimization.
12. Never introduce an LLM call when deterministic logic is sufficient.
13. Never introduce screenshots when DOM/CDP is sufficient.
14. Never launch a new browser if an existing session can be reused.
15. Preserve browser authentication state.
16. Keep secrets and session credentials out of model context.
17. Ask for human interaction for CAPTCHA/MFA/security prompts.
18. Document architectural decisions.

 The improvement between run #1 and run #2 is a core product demonstration.

 # 51\. Ultimate Vision

 The final system should feel like:

 > "Tell the agent what you want done in your existing browser. It understands the task, uses the browser you are already logged into, handles complex modern websites, asks for help only when necessary, remembers how it solved previous tasks, and gets faster over time."

 Not:

 > "A giant LLM repeatedly looks at screenshots and clicks things."

 The fundamental engineering objective is:

 # Maximum browser capability with minimum AI overhead.

 # 53\. Final Product Principle

 The system should always ask:

 > "Can I do this without AI?"

 If yes:

 **do it deterministically.**

 If not:

 > "Can I solve it from DOM?"

 If yes:

 **use DOM.**

 If not:

 > "Can a small model solve it?"

 If yes:

 **use small model.**

 If not:

 > "Do I really need vision?"

 If yes:

 **use vision.**

 If security or ambiguity requires a human:

 **pause and ask the human.**

 This hierarchy is the central idea of BrowserSkill Ultra.

Iya — kalau kriterianya **harus bisa menangani website berat/modern seperti LinkedIn, Instagram, Microsoft Entra, SSO, MFA, SPA, iframe, extension, dan login session asli**, saya justru **tidak akan mengganti BrowserSkill dengan Lightpanda**. BrowserSkill punya keunggulan arsitektural yang penting: dia mengendalikan **Chrome/Edge yang benar-benar dipakai user**, termasuk login state yang sudah ada, dan punya human-in-the-loop untuk CAPTCHA/login/confirmation.  GitHub+1

 Tapi kita bisa bikin **racikan OSS yang jauh lebih agresif soal performance**.

 ## Racikan yang saya pilih

```
                    USER
                     │
                     ▼
              ┌──────────────┐
              │ Fast Router  │
              │  ~1-5 ms     │
              └──────┬───────┘
                     │
       ┌─────────────┼──────────────┐
       │             │              │
       ▼             ▼              ▼
   DOM action     CDP action     Vision/LLM
   deterministic  deterministic   fallback
       │             │              │
       └─────────────┼──────────────┘
                     ▼

             │ Chromium      │
             │ real profile  │

             └───────┬───────┘
                     │
                     ▼
               Internet
```

 Dan saya akan memakai:

 - **Chromium/Chrome/Edge asli** sebagai engine utama.
- **CDP** sebagai transport/action layer.
- **Playwright** untuk deterministic actions.
- **Stagehand** hanya sebagai AI primitive (`observe`, `act`, `extract`), bukan sebagai agent loop utama. Stagehand memang dirancang sebagai layer AI di atas Playwright.  GitHub
- **BrowserSkill-style extension/session bridge** untuk mempertahankan login/session/user profile.
- **LLM router kecil** untuk menentukan kapan AI benar-benar diperlukan.
- **Vision/Computer Use** hanya sebagai _last resort_.

```

     ↓
```
